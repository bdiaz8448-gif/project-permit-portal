## What this is
A digital construction permit request system (pilot/beta) for the DSM project. Replaces the spreadsheet-based daily permit log. Contractors ("trade partners") request permits from their phones; Jacobs reviews and approves; everything is tracked, numbered, and exportable.

## The entire app is ONE file: `index.html`
- Plain HTML + CSS + vanilla JavaScript. No build step, no framework, no server.
- Open it in any browser and it works. All data saves to that browser's localStorage (key `ppp_db_v1`).
- `assets/` = floor plan images (extracted from the DSM4 floor plans PDF).
- `w4rw4/` = the real permit form PDFs (Hot Work, Confined Space, etc.), linked from the Permit Forms tab.
- The two `MASTER Permits` .xlsx files are the ORIGINAL spreadsheet logs the app replaced — keep for reference.

## Key facts an AI needs before editing
- **Data model:** everything lives in a `DB` object (see `SEED` + `migrate()` near the top of the script). Schema changes MUST go through `migrate()` with a version bump (`DB._v`) so existing users' saved data upgrades cleanly.
- **Views:** hash-routed. Every screen is a function on `VIEWS` (e.g. `VIEWS.dashboard`) returning an HTML string, rendered by `route()`.
- **Roles:** contractor (Trade Partner Supervisor, no PIN), safety (Trade Partner Safety Manager, per-person PIN, view-only, own company only), jacobs (shared PIN), admin (per-person PINs), owner (special admin PIN — default 7777 — unlocks Activity Log, Trash, restore tools).
- **Permit numbers:** `BUILDING-TYPE-###` (e.g. D4-HW-028), generated by `nextPermitNumber()`, never reused (counters only go up, even after deletes).
- **Workflow:** 3 steps — submit lands "Under Review" → approve makes it "Active" → contractor foreman marks "Completed". Other statuses (Needs Update, Rejected, Void, Lost, Expired) still exist.
- **Escalation clock** starts at scheduled work start time (or submission if later). Yellow at `remind1` min (default 15, supervisor escalation), red URGENT at `remind2` (default 30, permit office). All gated by `notifyActive()` (owner on/off + day schedule).
- **Notifications are one-tap `sms:`/`mailto:` links** (pilot limitation — a static file can't send messages itself). "Auto" mode opens the pre-filled text automatically on submit. TRUE automatic sending needs the cloud version (Supabase + Twilio) — that's the known next step.
- **Languages:** EN/ES via the `ES` dictionary + `T()` function. New user-facing strings should be added to the dictionary.
- **Testing habit:** changes were verified by extracting the `<script>` into Node with DOM mocks. At minimum, check syntax with: `node -e "new Function(require('fs').readFileSync('index.html','utf8').match(/<script>([\s\S]*)<\/script>/)[1])"`.

- **Live site:** https://bdiaz8448-gif.github.io/project-permit-portal/ (GitHub Pages, repo `bdiaz8448-gif/project-permit-portal`). To update: re-upload index.html to the repo, commit, wait ~1 min.
- **Cloud sync (done):** Supabase project `project-permit-portal` (ref `ltjvpodpdlmwvjmwuygm`), owned by the same GitHub account. Two tables: `permits(id text pk, updated bigint, deleted bool, data jsonb)` and `portal_config(id int pk, updated bigint, data jsonb)`. The site syncs via PostgREST with the publishable key embedded in index.html (search `CLOUD=`). Push on every save (1.2s debounce), pull every 15s + on tab focus; per-permit last-write-wins by `_u` timestamp; config row id=1 by `cfgU`. Footer badge shows sync state. All devices now share the same live data.
- Supabase dashboard: supabase.com/dashboard → sign in with GitHub.

## Pilot limitations (by design)
1. QR codes point at the live URL above — reprint if hosting moves.
2. No file attachments, no digital signatures yet.
3. Anyone with the site URL can read/write the pilot database (publishable key, no row security) — fine for a pilot, add Supabase Auth + RLS before selling.
4. Rare same-second edits to the SAME permit on two devices: last write wins.
